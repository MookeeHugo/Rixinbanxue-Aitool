# 题库与日新教育平台对接分析报告

## 1. 项目现状综述

### 1.1 题库解析端（question-entry-tool）
- 技术栈：Next.js 14.2.7 + React 18.3.1 + TypeScript + Tailwind 3.4.17 + shadcn/ui，使用 Zustand 维护上传/任务状态，具备上传、解析列表、QuestionEditor、QuestionLibrary、Admin Dashboard 等页面。
- 当前问题：仍然完全依赖 mock 数据，没有任何 `app/api/*` Route Handler，也没有连接 Supabase、Cloudflare R2 等真实后端。任务恢复、解析进度、Admin 面板等组件均只在前端 store 中读写。
- 配置缺失：仓库缺少 `.env`、锁文件与统一的脚本说明，无法在 CI 或多环境中复现；本地上传逻辑只走 `mockAPI.uploadSingleFile`，没有接入鉴权或限额。

### 1.2 日新教育平台（`D:\rixinwork\Rixindemo-codex-m1`）
- 技术栈：Next.js 14 + React 18 + Supabase + Cloudflare R2 + Ant Design + shadcn/ui，配有 `scripts/start-local-dev.mjs` 一键启动脚本。
- 数据层：`supabase/migrations` 已落地 `profiles/classes/questions/papers/assignments/submissions/export_tasks` 等表，并启用严格 RLS，`supabase/seed.sql` 提供演示账号。
- API 层：所有 `src/app/api/...` 路由直接使用 Supabase server client，具备题目增删、导出、直播、班级等真实业务能力。
- 存储/鉴权：`src/lib/storage.ts` 已封装 R2 上传、签名与删除逻辑，`.env.local.example` 列出了 Supabase/R2/Redis/钉钉告警等配置。

## 2. 对接就绪评估

| 维度 | 题库解析端 | 日新教育平台 | 对接影响 |
| --- | --- | --- | --- |
| 数据模型 | 文档规划了 `upload_tasks/parsed_questions/question_images/question_tags`，但数据库未创建 | 已有 `questions` 等核心表 | 需要统一 schema 或在解析端内部做映射，否则无法直接写入主库 |
| API 实现 | 缺少真实后端，仅有 mock API，上传/解析/批量提交均未落地 | Route Handler 完备 | 解析端必须补齐接口能力，才能供主平台调用 |
| 鉴权模式 | 页面不使用 Supabase Auth，也没有 JWT 注入 | 依赖 Supabase Auth + RLS，BFF 通过 `getUser()` 校验 | 解析 API 必须接受 Supabase token/tenant 信息，才能安全写库 |
| 文件存储 | 没有连接 OSS/CDN，仅模拟上传 | 共用 Cloudflare R2 + CDN | 必须复用同一 Bucket+Key 规则，才能被题库/导出模块访问 |
| 环境配置 | 缺少 `.env`、脚本、CI 配置 | `.env.local.*`、Supabase CLI、Playwright 等完备 | 解析端需补齐基础设施，保证可部署/可测试 |
| 模型策略 | 方案里描述多供应商，但未落地 | 平台暂未使用 AI | 对接前需确定 MVP 的模型（现决定先全部使用 Qwen） |

结论：解析端尚不具备直接接入的条件，必须完成后端化、统一数据契约、与平台共享鉴权与存储后，才能上线。

## 3. 深度分析与实施路径

### 3.1 解析端后端化
1. 新增 `app/api/upload/*`、`app/api/tasks/*`、`app/api/questions/*` Route Handler，使用 Supabase server client（服务密钥或用户 token）。
2. 将上传 → 校验 → 写入 R2 → 创建 `upload_tasks` → 推送解析任务等逻辑固化在 API 中，返回统一的 `{ success, data, error }` 响应。
3. 引入 Worker（BullMQ/Inngest）处理 OCR/LLM 解析；任务日志写入 `provider_usage_logs`，供排查与成本统计。

### 3.2 统一数据契约
- 方案A：在 Supabase 中创建 `upload_tasks/parsed_questions/question_images/question_tags/provider_usage_logs/tenant_quotas`，两个项目共享数据库，解析端直接写表，主平台即刻可读。
- 方案B：解析端自建轻量数据库，仅在入库阶段调用主平台 BFF 写入 `questions`。该方案需要额外的数据同步、权限校验和备份，不建议在 MVP 阶段采用。
- 推荐方案A：共享数据库 + 共享 R2，可减少跨系统同步，RLS 通过 `user_id/tenant_id` 保障隔离。

### 3.3 鉴权与安全
- 前端继续使用 Supabase Auth 登录，获取 `access_token`。调用解析 API 时附带 `Authorization: Bearer <token>`，API 在服务端用 `createClient` 验证。
- 解析 Worker 写系统表时使用 Service Role Key，但必须部署在受控环境，并结合 IP allowlist、签名等手段避免滥用。
- BFF 负责注入 `traceId`、`tenantId` 等上下文，所有日志与告警以 `traceId` 串联。

### 3.4 文件存储一致化
- 复用 `src/lib/storage.ts` 中的上传、签名、删除逻辑，统一在 R2 中以 `raw-papers/{tenant}/{taskId}.pdf`、`questions/images/{questionId}/{index}.png` 命名。
- 将 `publicUrl` 和 `file_key` 一并写库，方便 QuestionEditor 与导出、删除时查找原始文件。

### 3.5 主平台 BFF 改造
- 新增 `/api/ingest/upload`、`/api/ingest/tasks/[id]`、`/api/ingest/tasks/[id]/questions`、`/api/ingest/batch`、`/api/ingest/quotas` 等路由，负责：
  1. 代理上传：校验 Supabase Session → 调用解析服务 → 返回 taskId。
  2. 轮询任务：统一错误处理、超时与 traceId。
  3. 批量提交：封装题目 payload 与人审修改，调用解析服务完成入库。
- 通过 BFF，浏览器无需直接暴露解析服务域名或 Service Key，后续切换模型/供应商时只需调整服务器配置。

### 3.6 联调、监控与测试
- 在 `scripts/start-local-dev.mjs` 中加入“启动解析服务”步骤，确保一键本地运行。
- 编写端到端脚本：上传 PDF → 解析 → 人工确认 → 批量入库 → Library 查看。
- 接入钉钉/企业微信告警：解析失败、模型不可用、任务超时、成本异常等都触发通知。

### 3.7 大模型策略（更新）
1. **MVP 阶段全部使用 Qwen**：OCR、VLM、标签推荐均使用 Qwen-VL 系列（如 Qwen-VL-Max）。
   - 优势：有成熟云 API，中文数学题识别准确度高；无需维护本地 GPU，可快速交付。
   - 解析流程：上传 → Qwen OCR/VLM → 文本切题 → Qwen LLM 生成标签/答案提示 → 人审。
2. **DeepSeek-OCR 作为后续可选项**：当前没有 SaaS 版本，只能自建或租 GPU。
   - 建议：如需验证 DeepSeek，可考虑「云托管部署」（GPU 服务器 + 镜像），减少自运维成本；待业务规模增大或需要低成本/隐私部署时再启用。
   - 届时 Provider Factory 已经搭好，新增供应商只需在 `provider_configs` 中配置。

## 4. 风险与建议
1. **数据一致性**：若解析端与主平台分别维护题目数据，极易出现版本漂移。建议以 Supabase 为唯一事实来源。
2. **鉴权绕过**：解析 Worker 使用 Service Key 写库时必须严格限制调用入口、记录审计日志，并在 BFF 层再做二次校验。
3. **模型单点风险**：MVP 阶段全部使用 Qwen，需向阿里云申请充足配额，并实现超时重试/熔断，避免解析任务堆积。
4. **工程欠缺**：解析端缺少 README、锁文件和 CI；需补齐 `pnpm-lock.yaml`、`.env.example`、`lint/test` 脚本以及 Supabase CLI 使用说明。
5. **成本控制**：即使只有 Qwen，也要实时记录 `page_count/token/cost`，并在 `tenant_quotas` 超限时拒绝任务或提示升级。

## 5. 结论
- 解析端尚不可直接对接，需要完成后端化、数据库迁移、鉴权、存储与 BFF 改造后，才能与主平台稳定联动。
- 推荐分阶段实施：共享数据层 → 实现解析 API/Worker → 平台 BFF 接入 → 人审/入库联调 → 配额与监控 → 再考虑多模型策略。
- 首批上线仅使用 Qwen，可快速验证闭环。DeepSeek-OCR 作为后续优化方案，可在云端托管或私有化部署后，通过 Provider Factory 无缝接入。

## 6. 前置任务交付（文档 + 方案 + 脚本）

### 6.1 API 与功能清单
| 模块 | Endpoint | 说明 | 依赖 |
| --- | --- | --- | --- |
| 文件上传 | `POST /api/upload/file` | 校验 + R2 上传 + 新建 `upload_tasks` + 返回 taskId | Supabase token、R2、Redis 队列（可选） |
| 任务查询 | `GET /api/upload/tasks/{taskId}` | 返回状态、进度、耗时、traceId | Supabase `upload_tasks` |
| 解析结果 | `GET /api/upload/tasks/{taskId}/questions` | 分页读取 `parsed_questions` | Supabase `parsed_questions` |
| 批量提交 | `POST /api/questions/batch` | 将选中题目写入 `questions/question_tags/question_images` 并更新 `is_submitted` | Supabase（RLS）+ R2 |
| 重新解析 | `POST /api/upload/tasks/{taskId}/reparse` | 重新投递整卷或单题 | Worker + Qwen API |
| 标签生成 | `POST /api/ai/tagging` | （可选）二次调用 Qwen 生成标签/题型建议 | Qwen LLM |

### 6.2 数据库与迁移
- 新增 `upload_tasks/parsed_questions/question_images/question_tags/provider_usage_logs/tenant_quotas`，所有文件均位于 `supabase/migrations`，并在 README 中标注执行顺序。
- 现有 `questions` 表补齐 `analysis_content/source/year/tags[]/image_key` 等字段，保证老数据迁移与 RLS 策略同步。

### 6.3 后端/API 技术方案
1. Web/API 层：Next Route Handler 或独立 Fastify 服务，负责鉴权、输入校验（Zod）、上传至 R2、写 `upload_tasks`。
2. Worker 层：BullMQ/Inngest + Redis，消费任务 → 下载文件 → 调用 Qwen OCR/LLM → 切题 → 写 `parsed_questions` → 更新状态。
3. 存储层：共享 R2，封装上传/删除/签名，所有 URL 与 Key 入库，支持 QuestionEditor 与删除回收。
4. BFF 层：Next14 API 代理解析服务，注入 token/traceId/tenantId，并统一错误码（如 `UNAUTHORIZED/QUOTA_EXCEEDED/PARSE_FAILED`）。
5. 日志/告警：记录 `traceId、provider_id、duration_ms、cost_estimated、success`，通过钉钉/企微发送异常。
6. 自动化：补充 `scripts/dev-ingest-service.mjs`，在 CI 中新增 `supabase-migrations` Job，确保迁移与测试可重复。

### 6.4 本地 Supabase 调试
- 可以与主平台共用 Supabase（推荐），解析项目 `.env` 直接指向相同 URL/Key。
- 若需独立运行，需在解析项目的 `supabase/config.toml` 中修改 `project_id` 与端口，或使用 `supabase start -p ingest-service`。
- 并行运行多个实例时，注意 `npx supabase stop` 清理陈旧容器，避免占用 `54321/54322/8000/9000`。

### 6.5 供应商策略
- MVP：全部使用 Qwen（OCR + VLM + LLM），只维护一个 `provider_id=qwen-vl-max`。
- 后续：在 `provider_configs` 中为 DeepSeek-OCR（云托管）预留配置字段（endpoint、priority、cost、适用场景），当成本或准确率需要优化时再启用。
- `provider_usage_logs` 记录 taskId、provider_id、stage、tokens、duration、cost、confidence、success/error_code，用于成本核算与 A/B 实验。

### 6.6 配额与成本控制
- `tenant_quotas` 记录 page/token/cost 三类资源，字段包含 `limit_value/used_value/window_start/window_end/overage_policy`。
- 上传前调用 `checkQuota`，占用页数；解析/LLM 后将 token、成本累加；失败则 `rollbackQuota`。
- 超额策略：`block`（拒绝新任务）、`queue`（排队等待）、`billable`（允许但记录超额费用），配合告警与套餐升级。

### 6.7 实施路线
1. **阶段一（共享数据层）**：完成 Supabase 迁移、.env 统一、R2 共享、解析端接入 Supabase。
2. **阶段二（解析端后端化）**：实现上传 API、Worker、Qwen 解析流水线、`parsed_questions` 写库。
3. **阶段三（BFF + 人审联调）**：主平台 `/api/ingest/*` 上线，QuestionEditor 接入真实数据，批量入库与 Library 验证。
4. **阶段四（配额+监控）**：接入 `tenant_quotas`、成本报表、告警、Admin 统计，为商业化铺路。
